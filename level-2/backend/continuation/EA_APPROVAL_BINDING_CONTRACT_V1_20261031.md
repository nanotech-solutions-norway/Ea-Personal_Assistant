# EA approval binding contract v1 — 02:20, 31.10.2026

Work ID EA-SYNC; architecture-neutral proposed source foundation, PENDING_REVIEW. PR109 tenant tests are accepted merged source and are preserved. No S/M selection, migration, runtime activation or live account/provider action.

Existing SQL `001_initial_schema.sql` gives ea_actions a case FK and ea_approvals separate case/action FKs. Those separate constraints do not prove that an approval's case equals its action's case. Existing `approval-envelope.schema.json` lacks tenant and action identifiers; `policy.assert_executable(approval_present=True)` is a policy-level boolean gate, not authenticated binding evidence. None of those existing contracts is silently changed.

The new optional pure `approval_binding.py` validator compares authenticated tenant, case/action/approval references, action type, current revision and exact payload hash, active status, approval eligibility and qualified validity times. Reservation identity uses structured tuple encoding. Existing `idempotency.action_revision` and `approval_payload_hash` generate test fixture digests. Caller must obtain authenticated tenant and freshly recomputed digest inputs from trusted sources; no approver authenticity is inferred from a string. Mandatory finite expiry is a conservative PROPOSED contract, not an amendment of the existing optional-expiry envelope.

The validator returns a reservation key only. It performs no provider I/O, mutation or persistent reservation and is deliberately not wired to live policy. A test-only locked reservation adapter demonstrates concurrent one-winner behavior, consumed-approval denial, tenant separation and uncertain-attempt retry rejection. It is NOT durable crash recovery: restarting a process discards that adapter, so production use is forbidden. A future S/M-qualified durable adapter must enforce transactionally unique tenant/approval and action/revision identity, persisted uncertain states and independent readback before any protected execution.

Reproduce from `level-2/backend`: `python -m unittest discover -s tests -v`. The existing backend PR workflow runs the added tests. Negative coverage includes cross-tenant/case/action reuse, missing principal, stale/malformed digest, changed payload/revision, expired/future/naive time, revoked/consumed/unknown state, prohibited action, concurrent duplicates, uncertain attempt and rebinding a consumed approval.
